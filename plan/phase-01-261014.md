# METRO — 서울을 달리는 뽀모도로

## Claude Code 프로젝트 마스터 프롬프트

### 1. 프로젝트 개요

**프로젝트명:** METRO (가칭)  
**서비스 유형:** 웹 기반 몰입형 뽀모도로 타이머 / 지하철 시뮬레이션  
**핵심 콘셉트:** 서울 지하철을 타고 목적지까지 이동하는 동안 집중하는 서비스

사용자가 집중할 시간을 설정하면 해당 시간에 적합한 실제 서울 지하철 구간을 추천한다.

사용자는 추천된 노선을 선택하거나 직접 출발역과 도착역을 선택할 수 있다.

집중을 시작하면 지하철 내부 창가 시점에서 서울의 풍경이 흘러가는 시뮬레이션이 재생된다.

열차는 실제 노선의 역 순서와 예상 소요시간에 기반하여 이동하며, 목적지에 도착하면 집중 세션이 종료된다.

서비스는 일반적인 생산성 도구가 아닌, **집중하는 시간을 하나의 작은 서울 여행으로 바꾸는 경험형 서비스**를 지향한다.

**핵심 슬로건**

> 집중하는 모든 순간이, 좋은 곳으로 데려다줄 거예요.

---

### 2. 개발 핵심 원칙

다음 원칙을 반드시 준수한다.

1. 시각적 완성도를 최우선으로 한다.
2. 실제 지하철에 탑승한 듯한 몰입감을 제공한다.
3. 현실적인 서울의 특징을 유지하면서 귀여운 스타일을 적용한다.
4. 기능을 많이 구현하는 것보다 핵심 경험을 정교하게 완성한다.
5. 불필요한 텍스트와 복잡한 UI를 최소화한다.
6. 애니메이션은 자연스럽고 부드러워야 한다.
7. 실제 지하철 경로 데이터와 시뮬레이션용 가상 데이터를 명확하게 구분한다.
8. 초기 버전은 회원가입이나 복잡한 백엔드 없이 동작할 수 있어야 한다.
9. 데스크톱 우선으로 구현하되 모바일 반응형도 고려한다.
10. 모든 디자인과 그래픽은 일관된 자체 스타일을 유지한다.

**특히 주의할 것**

이 프로젝트를 일반적인 대시보드, 카드 목록형 생산성 SaaS, 또는 단순 노선도 애니메이션으로 만들지 말 것.

사용자가 가장 많은 시간을 보내는 화면은 집중 중 시뮬레이션 화면이다.

따라서 개발 리소스를 이 화면에 우선 배분한다.

### 3. 핵심 사용자 시나리오

#### 3.1 집중시간 설정

사용자는 서비스에 접속하면 다음 화면을 만난다.

메인 타이틀:

"오늘은 어디로 떠날까요?"

서브 카피:

"집중하는 동안, 서울의 한 구간을 함께 달려요."

집중시간 선택 옵션:

- 15분
- 25분 (기본)
- 40분
- 60분
- 사용자 직접 입력

선택적으로 오늘 집중할 작업을 입력할 수 있다.

예시: "사이드 프로젝트 개발하기"

시간 선택 시 다음 화면에서 해당 시간에 적합한 노선을 추천한다.

#### 3.2 노선 추천

설정한 집중시간에 가장 근접한 예상 이동시간을 가진 지하철 노선을 추천한다.

추천 카드에 표시할 정보:

- 지하철 호선
- 출발역
- 도착역
- 예상 운행시간
- 경유역 수
- 주요 풍경 키워드
- 구간 미리보기 이미지

예시:

"2호선 · 당산 → ○○역"

"한강 철교를 지나 도심으로 향하는 여행"

추천 경로는 실제 지하철 데이터에 기반해야 한다.

25분을 선택했다고 해서 실제 3분 구간을 25분 노선이라고 표시하지 않는다.

실제 예상시간과 사용자의 설정시간이 다른 경우에는 차이를 명시하고, 집중모드에서 애니메이션 재생 시간을 조정할 수 있다.

또한 사용자가 직접 출발역과 도착역을 선택할 수 있도록 한다.

초기 MVP에서는 2호선을 중심으로 구현한다.

#### 3.3 집중 시작

사용자가 '출발하기'를 누르면 시뮬레이션 화면으로 이동한다.

처음에는 출발역 플랫폼에 열차가 정차해 있다.

이후 다음 과정으로 시작된다.

1. 출발 알림음
2. 출입문 닫힘 효과
3. 열차의 부드러운 가속
4. 플랫폼 이탈
5. 터널 또는 지상 구간 진입
6. 창밖 풍경 이동
7. 다음 역 접근
8. 감속 및 정차
9. 다음 역 출발

위 과정이 목적지까지 반복된다.

#### 3.4 집중 완료

열차가 목적지에 도착하면 집중 세션이 종료된다.

완료 화면에는 다음 정보가 표시된다.

- 출발역과 도착역
- 완료한 집중시간
- 방문한 역 수
- 이동한 거리 (실제 데이터가 확보된 경우)
- 오늘 누적 집중시간

지하철 승차권 형태의 완료 카드를 제공한다.

사용자는 결과를 저장하거나 이미지로 공유할 수 있다.

### 4. 핵심 시각 디자인

#### 4.1 디자인 방향

**Cozy Seoul × Miniature Realism × Subway Journey**

현실적인 서울을 기반으로 하지만 실제 영상과 같은 극사실주의를 추구하지 않는다.

전체적인 느낌은 다음과 같다.

- 따뜻하고 편안한 분위기
- 정교한 미니어처 또는 디오라마 스타일
- 귀여운 비율의 건물과 사물
- 은은한 파스텔 색상
- 부드러운 자연광
- 적절한 입체감과 그림자
- 실제 서울의 특징을 알아볼 수 있는 풍경
- 귀여운 캐릭터 요소를 소량 활용

3D 애니메이션 영화의 따뜻한 분위기를 참고하되, 특정 제작사의 고유한 캐릭터나 디자인을 복제하지 않는다.

일반적인 평면 벡터 일러스트 수준에서 끝나지 않도록 한다.

#### 4.2 디자인 시스템

기본 색상:

- Primary: Subway Green (#2E946B)
- Background: Warm Ivory (#F7F5F1)
- Surface: White (#FFFFFF)
- Text: Charcoal (#252525)
- Secondary: Gray (#858585)
- Accent: Soft Orange (#F4B36B)

이 색상은 초기 제안이며 화면에서 검증한 후 디자인 토큰으로 확정한다.

타이포그래피는 Pretendard 또는 적합한 한글 웹폰트를 사용한다.

카드와 인터페이스는 적당한 Border Radius를 적용하고, 그림자는 약하게 사용한다.

과도한 Glassmorphism, Gradient, AI 생성 대시보드 스타일을 지양한다.

Vercel Design의 절제된 인터페이스를 참고하되 서비스의 귀여운 시각적 정체성을 우선한다.

### 5. 가장 중요한 화면: 지하철 창밖 시뮬레이션

이 프로젝트에서 가장 많은 개발 역량을 투입할 부분이다.

#### 5.1 카메라 시점

실제 서울 지하철 내부의 창가 좌석에 앉아 바깥을 바라보는 시점을 기본으로 한다.

화면 구성:

- 전체 화면의 약 70~80%를 창밖 시뮬레이션 중심으로 구성
- 지하철 내부 창문 프레임
- 창가 주변 벽과 손잡이 일부
- 좌석 일부
- 창밖을 지나가는 서울 풍경
- 상단 노선 및 현재 역 정보
- 중앙 또는 하단의 남은 집중시간
- 하단 역 진행 표시
- 사운드와 일시정지 컨트롤

UI가 시뮬레이션을 지나치게 가리지 않도록 한다.

집중시간과 현재역 정보는 한눈에 확인할 수 있어야 한다.

#### 5.2 실제 지하철 내부 디테일

다음 요소를 적절히 구현한다.

- 둥근 모서리의 지하철 창문
- 실내 조명
- 서울 지하철 느낌의 좌석 패턴
- 손잡이와 창문 테두리
- 현재역 안내 디스플레이
- 창문에 비치는 약한 실내 반사
- 캐릭터 스티커 또는 작은 마스코트

단순히 배경 영상 위에 타이머를 올리는 방식이 아니라 실제 지하철 실내에서 창밖을 보는 공간감을 제공해야 한다.

#### 5.3 창밖 배경 구현

초기 단계에서는 서울 전체를 3D로 재현하지 않는다.

대신 2.5D Parallax 시뮬레이션을 구현한다.

배경을 다음 레이어로 구분한다.

1. Sky Layer — 하늘과 구름
2. Distant Layer — 산, 먼 스카이라인
3. City Layer — 건물, 아파트, 상가
4. Near Layer — 가로수, 철도 구조물, 방음벽
5. Foreground Layer — 빠르게 지나가는 기둥과 근접 사물

레이어별 이동속도를 다르게 적용하여 자연스러운 깊이감을 만든다.

반복되는 패턴이 눈에 띄지 않도록 배경 조합, 간격, 원근감, 출현 위치를 다양화한다.

애니메이션은 일정 속도의 단순 반복이 아니라 가속·감속·정차 상태를 가진다.

### 6. 서울 풍경 시뮬레이션

초기에는 다음 5가지 장면을 구현한다.

#### Scene A. 지상 주거지

- 서울의 아파트
- 낮은 상가 건물
- 멀리 보이는 산
- 전신주와 철도 시설물
- 도심의 소소한 풍경
- 낮 시간의 따뜻한 햇살

#### Scene B. 한강 철교

가장 높은 완성도가 필요한 대표 장면이다.

- 넓게 펼쳐진 한강
- 강 위로 이어지는 철교 구조물
- 멀리 보이는 서울의 스카이라인
- 한강공원 및 녹지
- 물 위에 반사되는 햇빛
- 실제 서울의 지리적 특징을 반영한 건물 배치

예시 구간: 2호선 당산역과 합정역 사이.

실제 열차 진행 방향과 창문이 바라보는 방향을 고려하여 주요 랜드마크를 배치한다.

#### Scene C. 도심 빌딩

- 업무지구의 높은 건물
- 상가와 도로
- 저녁 시간대의 실내조명
- 원근감 있는 도심 스카이라인

실제 노선의 지상·지하 특성을 확인하여 해당 구간에서 볼 수 있는 풍경만 사용한다.

#### Scene D. 지하 터널

- 어두운 터널
- 반복되는 터널 조명
- 터널 벽면 구조물
- 지나가는 케이블과 시설물
- 창문에 비치는 실내 반사
- 열차 속도에 따른 자연스러운 움직임

지하 구간의 대부분은 터널 장면으로 표현하되 너무 단조롭지 않도록 조명과 구조물을 다양화한다.

#### Scene E. 역사 진입 및 정차

- 플랫폼 접근
- 감속 애니메이션
- 역명 표지판
- 승강장 스크린도어
- 역 조명
- 승강장 정차
- 출발 및 가속

역별 명칭은 실제 데이터와 일치해야 한다.

### 7. 시뮬레이션 엔진 설계

시뮬레이션의 핵심 상태는 다음과 같이 관리한다.

- IDLE
- BOARDING
- DEPARTING
- MOVING
- APPROACHING
- ARRIVED
- PAUSED
- COMPLETED

각 상태는 시간 기반으로 전환된다.

역과 역 사이의 구간은 독립적인 Segment로 정의한다.

각 Segment가 가져야 할 정보:

- 출발역
- 도착역
- 기준 소요시간
- 풍경 유형
- 지상/지하 여부
- 이동 방향
- 주요 랜드마크
- 애니메이션 설정

시뮬레이션 엔진은 이 데이터를 바탕으로 장면을 결정한다.

예시 데이터 모델:

```
type SceneType =
  | "tunnel"
  | "residential"
  | "river"
  | "downtown"
  | "station";

interface RouteSegment {
  id: string;
  fromStationId: string;
  toStationId: string;
  durationSeconds: number;
  sceneType: SceneType;
  landmarks: string[];
  direction?: string;
}
```

경로 전체 소요시간과 사용자의 집중시간은 구분한다.

실제 운행시간보다 집중시간이 길거나 짧으면 각 Segment의 재생시간을 비례 조정하는 시뮬레이션 모드를 제공한다.

단, 실제 운행시간을 변경한 것처럼 표시해서는 안 된다.

타이머는 프레임 누적 방식이 아닌 실제 경과시간에 기반해야 한다.

탭 비활성화, 렌더링 지연, 브라우저 크기 변경에도 집중시간의 정확성을 유지한다.

일시정지와 재개 시 상태가 일치해야 한다.

브라우저 새로고침 복구 정책도 명확히 정의한다.

### 8. 실제 서울 지하철 데이터

데이터 소스 후보:

- 서울교통공사 최단경로 API
- 서울시 지하철 역 정보
- 지하철역 좌표 데이터
- 역별 예상 운행시간 데이터
- 서울시 공공데이터 포털
- 서울시 S-Map (활용 가능 범위 확인용)

공식 데이터의 실제 이용 가능 여부와 최신 제공 조건을 조사한다.

API의 인증, 호출 제한, 운영 승인, 라이선스 등을 확인한다.

외부 3D 건축물이나 지도 데이터는 사용 권한을 확인하기 전까지 직접 서비스에 복제하거나 포함하지 않는다.

공식 데이터가 즉시 사용 가능하지 않다면 초기에는 검증된 일부 구간을 정적 JSON 데이터로 관리한다.

정적 데이터에는 출처와 기준일을 기록하고, 검증 전에는 예상 운행시간으로 표시한다.

**노선 추천 알고리즘**

1. 사용자가 집중시간 선택
2. 해당 시간에 근접한 경로 검색
3. 노선과 역 순서 검증
4. 추천 구간 선별
5. 주요 풍경 정보 연결
6. 최종 추천 카드 생성

추천 경로는 이동시간 오차와 풍경 다양성을 함께 고려한다.

MVP에서는 환승 없는 2호선 구간을 우선 지원한다.

### 9. 인터랙션 및 사운드

열차는 시작 직후 최대 속도로 움직이면 안 된다.

출발할 때는 자연스럽게 가속하고, 역에 가까워지면 감속한다.

역 도착 시 짧은 정차 애니메이션을 제공한다.

사운드는 다음 요소를 준비한다.

- 열차 주행음
- 철도 레일 소리
- 역 도착 알림음
- 문 열림·닫힘
- 안내방송 스타일의 효과음
- 잔잔한 Ambient Sound

모든 사운드는 개별적으로 음소거 또는 볼륨 조절할 수 있어야 한다.

초기에는 라이선스가 명확한 사운드 또는 자체 제작 효과음을 사용한다.

브라우저 자동재생 정책을 준수하고 사용자의 명시적인 시작 동작 이후 오디오를 재생한다.

과도한 화면 흔들림과 번쩍임은 금지한다.

모션 감소 설정을 지원한다.

### 10. 부가 기능

#### 10.1 집중 완료 승차권

세션 종료 시 승차권을 생성한다.

표시 항목:

- 출발역
- 도착역
- 집중시간
- 이동한 역 수
- 완료 날짜
- 작은 일러스트
- 서비스 로고

이미지로 저장하거나 공유할 수 있도록 한다.

#### 10.2 나의 서울 노선도

완료한 집중 구간을 서울 지하철 노선도에 기록한다.

- 방문한 역
- 완료한 구간
- 누적 집중시간
- 총 운행 횟수

방문한 구간은 색상으로 표시한다.

기본적으로 이전 집중 세션의 도착역에서 다음 세션을 시작할 수 있다.

단, 초기에는 브라우저 LocalStorage 또는 IndexedDB에 저장하고 사용자 계정 기능은 후순위로 둔다.

#### 10.3 시간대별 풍경

초기 구현:

- 낮
- 노을
- 밤

한국 시간 기준으로 기본 장면을 선택한다.

사용자가 직접 시간대를 변경하는 옵션도 추후 확장 가능하도록 구조를 설계한다.

날씨 API 연동은 MVP에서 제외한다.

### 11. 기술 스택

다음 기술을 우선 검토한다.

**Frontend**

- Next.js
- React
- TypeScript
- SCSS Modules 또는 적합한 스타일링 시스템

**Animation**

- GSAP
- PixiJS (필요 시)
- Canvas 2D

**State**

- Zustand

**Data**

- Static JSON
- Public API Adapter
- LocalStorage / IndexedDB

**Deployment**

- Vercel

초기에는 불필요한 백엔드나 데이터베이스를 도입하지 않는다.

실제 서울 전체를 재현하는 Three.js 기반 3D 월드는 초기 개발 범위에서 제외한다.

2.5D 연출만으로 만족스러운 결과를 만들 수 있는지 먼저 검증한다.

반드시 전체 화면을 Canvas로 구현할 필요는 없다.

일반적인 UI는 DOM으로 구성하고, 움직이는 풍경과 그래픽 영역만 Canvas 또는 PixiJS로 구현하는 방향을 우선 검토한다.

### 13. 품질 기준

다음 사항을 구현 완료 기준으로 삼는다.

**시각적 품질**

- 지하철 창밖이라는 시점이 즉시 이해되어야 한다.
- 창밖에 실제로 움직이는 풍경이 존재해야 한다.
- 배경은 단순 이미지 슬라이드에 그치지 않아야 한다.
- 레이어별 시차와 자연스러운 이동감이 있어야 한다.
- 한강 철교, 플랫폼, 터널이 서로 명확하게 구별되어야 한다.
- 화면은 따뜻하고 귀여우면서도 유치하지 않아야 한다.

**기능적 품질**

- 선택한 집중시간에 맞춰 타이머가 동작해야 한다.
- 일시정지와 재개가 정확해야 한다.
- 역 순서 및 진행률이 일치해야 한다.
- 완료 시 중복 기록이 생성되지 않아야 한다.
- 새로고침에 대한 복구 정책이 적용되어야 한다.
- 실제 경로 데이터와 연출용 데이터를 구분해야 한다.

**성능**

- 일반적인 데스크톱 브라우저에서 부드러운 애니메이션을 목표로 한다.
- 가능하면 60fps를 목표로 하되 저사양 환경에서는 그래픽 품질을 낮출 수 있어야 한다.
- 화면이 보이지 않을 때 불필요한 렌더링을 줄인다.
- 메모리 누수나 불필요한 리소스 재생성을 방지한다.
- 화면 크기 변화에도 레이어의 비율과 위치가 깨지지 않아야 한다.

### 14. Claude Code 작업 지침

프로젝트 진행 시 다음 지침을 따른다.

1. 현재 프로젝트 구조와 기존 코드를 먼저 확인한다.
2. 기존 코드가 존재한다면 불필요한 파일 삭제나 전체 재구성을 하지 않는다.
3. 요구사항을 분석하고 아키텍처를 설계한다.
4. 단계별 구현 계획을 Markdown으로 기록한다.
5. 코드와 디자인 규칙을 [CLAUDE.md](http://CLAUDE.md)에 정리한다.
6. 범위가 큰 기능은 작은 단위로 나누어 구현한다.
7. 구현 후 빌드·타입 검사·기능 검증을 실행한다.
8. 임시 이미지, 목업, 실제 데이터의 차이를 명시한다.
9. 작동하지 않는 UI를 완성된 기능인 것처럼 만들지 않는다.
10. 각 Phase가 끝나면 구현한 기능과 미구현 항목을 정리한다.

특히 디자인 구현에서는 다음 사항을 금지한다.

- 이모지로 주요 그래픽 대체
- 단순한 직사각형 건물의 무의미한 반복
- 임의의 실사 배경 한 장을 반복 스크롤하는 방식
- 불필요한 텍스트 중심 UI
- 완성되지 않은 버튼을 실제 기능처럼 표시
- 성능을 고려하지 않은 무분별한 애니메이션
- 존재하지 않는 실제 지하철 데이터 생성

### 15. 최초 실행 지시

이제 프로젝트 구축을 시작한다.

먼저 다음 작업을 수행한다.

1. 요구사항을 검토하고 구현 리스크를 분석한다.
2. 개발에 가장 적합한 아키텍처를 선정한다.
3. 프로젝트 및 문서 구조를 생성한다.
4. Phase 1의 시각 중심 시뮬레이션을 우선 구현한다.
5. 로컬 환경에서 실행 가능한 상태로 만든다.
6. 실제 브라우저 환경에서 확인 가능한 경우 시각 결과를 검증하고 개선한다.

**첫 번째 목표는 실제 서비스 전체가 아니다.**

가장 먼저 완성해야 하는 결과물은 다음과 같다.

> 사용자가 서울 지하철 창가에 앉아 있고, 귀엽고 정교하게 표현된 서울 풍경이 자연스럽게 지나가며, 한강 철교를 건너는 동안 집중 타이머가 작동하는 웹 화면.

이 첫 번째 결과물의 완성도가 프로젝트의 향후 개발 방향을 결정한다.

따라서 화면의 완성도를 충분히 확보하기 전까지 인증, 커뮤니티, 통계 대시보드 등의 부가 기능 구현에 시간을 사용하지 않는다.

계획과 문서 작성에만 그치지 말고 Phase 1의 실제 동작하는 구현까지 진행한다.

프로젝트를 실제 제품으로 발전시킬 수 있도록 유지보수성, 확장성, 시각적 품질을 모두 고려하여 작업한다.
